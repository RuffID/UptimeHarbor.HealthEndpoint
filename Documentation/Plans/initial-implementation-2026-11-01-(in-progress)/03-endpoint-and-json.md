# 03. Реализовать маршрут и фиксированный JSON-контракт

Статус: `completed`.

## Цель

Подключить анонимный GET endpoint с фиксированным JSON-контрактом к существующему pipeline приложения.

## Зависимости

[Этап 02 — настройки и снимок процесса](02-configuration-and-process-start.md).

## Работы

Подключить GET через существующий endpoint routing; получить путь из валидированных options; обеспечить anonymous metadata, `200`, `application/json`, `name` и `startedAtUtc`. Использовать отдельные настройки System.Text.Json, не наследуя и не меняя naming policies и converters приложения. Запретить кеширование на стороне endpoint с учётом стандартных cache middleware. Поддержать переопределение Path без обнаружения конфликтов и повторных вызовов. Не удалять и не заменять чужие endpoints. Не добавлять проверки БД и других зависимостей.

## Затрагиваемые части

Проект библиотеки, локальные инструкции, Public API, Architecture, Configuration and validation, Consumer integration.

## Проверки

Анонимный запрос при fallback authorization, точный JSON под изменёнными глобальными настройками, отсутствие влияния на остальной JSON приложения, наличие no-store и взаимодействие со стандартным caching. Проверить `/health` и переопределённый свободный Path, отсутствие скрытой регистрации при Map без Add и утечки диагностических деталей в ответ. Однократное подключение — предусловие использования; специальных тестов защиты от повторов или стартового обнаружения конфликтов не требуется. Polling не порождает собственный Information-лог на каждый запрос.

## Критерии приёмки

Согласованный GET-контракт соблюдён при однократном Add/Map и свободном Path, JSON независим от настроек приложения, ответственности за маршрут и повторы описаны явно. Интеграционные проверки планируются в памяти без реальной сети; запуск только в отдельно разрешённом объёме.

## Результат

Реализован MapUptimeHarborHealth с закреплённой сигнатурой. GET использует неизменяемый снимок, отдельные read-only JsonSerializerOptions и внутреннюю модель с двумя полями. Время сериализуется с +00:00. Map без Add выдаёт безопасную ошибку до подключения маршрута; скрытых регистраций нет. Path переводится через PathString.FromUriComponent для сопоставления с декодированным Request.Path, исходная настройка сохраняется.

Завершающая convention добавляет AllowAnonymous и собственную IOutputCachePolicy, отключающую output cache lookup/storage/locking. Cache-Control: no-store запрещает стандартный response cache. Обычные conventions и авторизованная route group проверены; произвольные пользовательские middleware/финальные conventions и внешние proxy остаются ответственностью приложения.

Отдельные compile-check библиотеки и тестового проекта выполнены без ошибок и предупреждений. После этапа 03 через Microsoft Testing Platform прошли 75 тестов: 57 прежних и 18 новых, ошибок/пропусков 0. В памяти вызваны настоящие routing, fallback authorization, response caching и output caching middleware без хоста/listener. Контрольный обычный endpoint действительно кешируется, health выполняется дважды; отдельный обычный JSON-ответ сохраняет глобальные naming policy и converter приложения. Проверены default/custom/Unicode/кодированный пути, PathBase, route group, неизменность ответа и Map без Add. Для HEAD/POST/PUT стандартная маршрутизация даёт 405 при отключённой fallback policy; при fallback authorization отказ метода может быть заменён авторизацией приложения.

При проверке кодированного пути воспроизведено несовпадение raw route с декодированным Request.Path; оно исправлено и регрессионная проверка проходит. Реальный HTTP, приложение, ОС-перезапуск, Linux и nginx не запускались: они остаются обязательной внешней приёмкой этапа 04, а не результатом этапа 03.
