# 03. Реализовать маршрут и фиксированный JSON-контракт

Статус: `not-started`.

## Цель

Подключить анонимный GET endpoint с фиксированным JSON-контрактом к существующему pipeline приложения.

## Зависимости

[Этап 02 — настройки и снимок процесса](02-configuration-and-process-start.md).

## Работы

Подключить GET через существующий endpoint routing; получить путь из валидированных options; обеспечить anonymous metadata, `200`, `application/json`, `name` и `startedAtUtc`. Использовать отдельные настройки System.Text.Json, не наследуя и не меняя naming policies и converters приложения. Запретить кеширование на стороне endpoint с учётом стандартных cache middleware. Поддержать переопределение Path без обнаружения конфликтов и повторных вызовов. Не удалять и не заменять чужие endpoints. Не добавлять проверки БД и других зависимостей.

## Затрагиваемые части

Проект библиотеки, локальные инструкции, Public API, Architecture, Configuration and validation, Consumer integration.

## Проверки

Анонимный запрос при fallback authorization, точный JSON под изменёнными глобальными настройками, отсутствие влияния на остальной JSON приложения, наличие no-store и взаимодействие со стандартным caching. Проверить `/health` и переопределённый свободный Path, отсутствие скрытой регистрации при Map без Add и утечки диагностических деталей в ответ. Однократное подключение — предусловие использования; специальных тестов защиты от повторов или стартового обнаружения конфликтов не требуется. Polling не порождает собственный Information-лог на каждый запрос.

## Критерии приёмки

Согласованный GET-контракт соблюдён при однократном Add/Map и свободном Path, JSON независим от настроек приложения, ответственности за маршрут и повторы описаны явно. Интеграционные проверки планируются в памяти без реальной сети; запуск только в отдельно разрешённом объёме.
