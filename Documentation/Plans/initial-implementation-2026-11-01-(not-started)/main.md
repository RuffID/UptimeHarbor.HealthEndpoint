# Первичная реализация UptimeHarbor.HealthEndpoint

Дата создания: 2026-11-01. Общий статус реализации: `not-started`.

## Основание, цель и текущее состояние

Основание — поручение подготовить независимую библиотеку для HTTP-контракта мониторинга UptimeHarbor. Согласованные требования находятся в [ТЗ](../../Business%20logic/Business%20requirements.md), фактический контракт потребителя — в [архитектуре](../../Technical%20documentation/Architecture.md#consumer-contract).

Сейчас созданы только `.slnx`, пустой `.csproj` на `net10.0`, навигация, инструкции и документация. Исходники, options, методы подключения и endpoint отсутствуют. Подготовка этого скелета не входит в этапы реализации и не переводит их в `in-progress`.

Цель будущих работ — подключаемый к существующему pipeline анонимный endpoint с точными именами JSON-полей и фактическим временем запуска процесса. Библиотека не владеет listener, портами, Kestrel, TLS, nginx, firewall, Docker и БД. Независимость от проектов UptimeHarbor обязательна; исходный репозиторий остаётся только источником контракта.

Согласованный объём: минимум .NET 10 / ASP.NET Core 10, без поддержки 8 и 9; поставка DLL прямой ссылкой из libs без NuGet и ProjectReference; автоматическое имя обрезается до 256, явное после Trim допускает 3–256 и иначе вызывает исключение при запуске. Endpoint подтверждает только способность приложения отвечать и использует отдельные настройки JSON. Конфликты маршрутов и повторное подключение библиотека не обнаруживает; разработчик обеспечивает свободный Path и один вызов Add до одного Map. Проверка синтаксиса Path при старте сохраняется.

## 01. Подготовить технический контракт реализации

Статус: `not-started`. Зависимости: отдельное поручение на реализацию.

Работы: определить точные namespace, сигнатуры и расположение будущих options, расширений и снимка процесса. Спроектировать стартовую валидацию Name/Path и изолированные настройки System.Text.Json в уже согласованном объёме. Предусмотреть DLL-поставку без собственных сторонних зависимостей. Не проектировать обнаружение конфликтов, специальную защиту от повторного Add/Map или readiness зависимостей. Повторное согласование выбранных продуктовых правил не требуется.

Затрагиваемые части: ТЗ, техническая документация, данный активный план и публичные контракты будущего проекта. Исходный UptimeHarbor не меняется.

Проверки: сверить проектируемый контракт с checker потребителя, включая максимум 256; не объявлять совместимыми непроверенные более новые версии .NET; убедиться, что зависимости, кеширование и сериализация не размывают согласованный HTTP-контракт.

Критерий приёмки: публичные сигнатуры и ответственность будущих компонентов закреплены в технической документации, не меняют согласованные требования и достаточны для этапа 02. Согласованные требования уже отражены в документах; технический результат данного этапа пока отсутствует.

<a id="stage-02"></a>
## 02. Реализовать настройки и снимок процесса

Статус: `not-started`. Зависимости: этап 01.

Работы: создать options и `IServiceCollection`-расширение; после Trim проверять явный Name на 3–256, автоматически полученный ApplicationName при превышении 256 обрезать с сохранением корректного Unicode. Не читать `.csproj`. Валидировать Name/Path при запуске; не генерировать замену пустому имени. Один раз получить фактический старт текущего процесса, нормализовать UTC и сохранить неизменяемый снимок до обработки запросов. Не заменять недостоверный источник текущим временем. Создать содержательный локальный `AGENTS.md` при появлении собственного кода.

Затрагиваемые части: проект библиотеки, его локальные инструкции, документация конфигурации и жизненного цикла. Тестовую инфраструктуру добавлять только в разрешённом объёме будущей реализации.

Проверки: границы явного имени 2/3/255/256/257 после Trim, допустимость 200, пустая строка, кириллица и внутренние пробелы без дополнительных запретов; автоматические имена длиной 1/2/256/257, обрезка длинного имени, пустое автоматическое значение, корректность Unicode на границе. Проверить ошибочные и допустимые пути. Убедиться, что ошибка настройки возникает при старте без первого запроса. Проверить освобождение временного Process и отсутствие fallback. Диагностика на английском, без дампа options/секретов и ложного сообщения об успешном запуске.

Критерий приёмки: минимальная и явная регистрация работают по утверждённому API; невалидные настройки останавливают запуск; снимок времени соответствует процессу и не изменяется при обращениях. Нужные compile-check и изолированные тесты выполняются лишь после разрешения. Результат пока отсутствует.

<a id="stage-03"></a>
## 03. Реализовать маршрут и фиксированный JSON-контракт

Статус: `not-started`. Зависимости: этап 02.

Работы: подключить GET через существующий endpoint routing; получить путь из валидированных options; обеспечить anonymous metadata, `200`, `application/json`, `name` и `startedAtUtc`. Использовать отдельные настройки System.Text.Json, не наследуя и не меняя naming policies и converters приложения. Запретить кеширование на стороне endpoint с учётом стандартных cache middleware. Поддержать переопределение Path без обнаружения конфликтов и повторных вызовов. Не удалять и не заменять чужие endpoints. Не добавлять проверки БД и других зависимостей.

Затрагиваемые части: проект библиотеки, локальные инструкции, Public API, Architecture, Configuration and validation, Consumer integration.

Проверки: анонимный запрос при fallback authorization, точный JSON под изменёнными глобальными настройками, отсутствие влияния на остальной JSON приложения, наличие no-store и взаимодействие со стандартным caching. Проверить `/health` и переопределённый свободный Path, отсутствие скрытой регистрации при Map без Add и утечки диагностических деталей в ответ. Однократное подключение — предусловие использования; специальных тестов защиты от повторов или стартового обнаружения конфликтов не требуется. Polling не порождает собственный Information-лог на каждый запрос.

Критерий приёмки: согласованный GET-контракт соблюдён при однократном Add/Map и свободном Path, JSON независим от настроек приложения, ответственности за маршрут и повторы описаны явно. Интеграционные проверки планируются в памяти без реальной сети; запуск только в отдельно разрешённом объёме. Результат пока отсутствует.

## 04. Проверить совместимость и принять endpoint

Статус: `not-started`. Зависимости: этап 03; проверяемая базовая платформа — .NET 10 / ASP.NET Core 10.

Работы: реализовать содержательные изолированные контрактные тесты, сверить результаты с фактическим checker UptimeHarbor без production project reference на него. Обновить документацию по реальному API и ограничениям. В изменённых C#-тестах использовать AAA-комментарии. Не менять потребителя ради прохождения контракта библиотеки.

Проверки: успешный ответ разбирается потребителем; `Z` и `+00:00` совместимы; имя после согласованной нормализации/обрезки, размер, корень и поля корректны; глобальные настройки JSON не меняют контракт. Время стабильно между запросами и соответствует старту процесса при поздней регистрации. Проверить .NET/ASP.NET Core 10 и доступность источника времени на фактически заявляемых ОС. Поддержку 8/9 не заявлять, более новые версии подтверждать отдельно. Изолированные тесты не доказывают изменение после реального перезапуска.

Ручная/внешняя приёмка отдельно: реальный перезапуск процесса, существующий middleware pipeline, nginx, отсутствие redirect и cache, стабильная маршрутизация экземпляра. Эти проверки требуют отдельного разрешения на запуск и сетевые действия. Их отсутствие отражать явно, не выдавать in-memory тест за проверку прокси или ОС.

Критерий приёмки: согласованные проверки пройдены на заявленной матрице, результаты и ограничения записаны; обязательная внешняя приёмка либо выполнена, либо её отдельный объём явно согласован владельцем продукта. Текущие документы скелета не являются таким согласованием. Результат пока отсутствует.
