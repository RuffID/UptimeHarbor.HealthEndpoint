## Подключение DLL

После завершения реализации и проверки DLL-поставки потребуется скопировать `UptimeHarbor.HealthEndpoint.dll` в `libs` рядом с `.csproj` целевого приложения. Затем добавить в проект приложения прямую ссылку:

```xml
<ItemGroup>
  <Reference Include="UptimeHarbor.HealthEndpoint">
    <HintPath>libs\UptimeHarbor.HealthEndpoint.dll</HintPath>
    <Private>true</Private>
  </Reference>
</ItemGroup>
```

Путь корректируется под фактическое расположение папки libs. `Private` предусматривает копирование библиотеки в выходной каталог приложения; фактический состав сборки и публикации необходимо проверить после реализации. Это пример для внешнего приложения, сейчас его файлы не изменяются.

Цель — поставка одной DLL библиотеки без собственных сторонних зависимостей. ASP.NET Core предоставляется целевым приложением и его framework reference `Microsoft.AspNetCore.App`; системные framework DLL не нужно копировать вручную в libs. Точный состав поставки проверяется при будущей сборке. При обновлении библиотечную DLL заменяют и пересобирают приложение-потребитель; NuGet и ссылка на исходный проект библиотеки для подключения не нужны.

## Подключение к существующему pipeline

Минимальная платформа приложения — .NET 10 / ASP.NET Core 10; проект библиотеки нацелен на `net10.0`. Версии 8 и 9 не поддерживаются, совместимость с более новыми версиями подтверждается отдельно. Сборка библиотеки проверена на Windows x64/.NET 10; прямое подключение DLL к другому приложению ещё не проверено.

После создания `builder`, до `builder.Build()`:

```csharp
builder.Services.AddUptimeHarborHealth();
```

После создания `app`, до `app.Run()`:

```csharp
app.MapUptimeHarborHealth();
```

Вариант явного имени и пути:

```csharp
builder.Services.AddUptimeHarborHealth(options =>
{
    options.Name = "orders-api";
    options.Path = "/health";
});

app.MapUptimeHarborHealth();
```

Эти фрагменты нужно встроить в существующий Program.cs в соответствующих местах; они не создают builder/app и не заменяют остальной код. Add доступен через `using Microsoft.Extensions.DependencyInjection`; тип options находится в `UptimeHarbor.HealthEndpoint`, Map — в `Microsoft.AspNetCore.Builder`. Сигнатуры реализованы; дополнительный MVC controller или второй listener не нужен. Сборка приложения с прямой DLL-ссылкой ещё не проверялась.

Без Name библиотека сама использует `IHostEnvironment.ApplicationName`, обычно имя запускаемой сборки/проекта. `.csproj` не читается. Автоматическое имя после Trim при длине больше 256 обрезается до 256; оно должно быть непустым. Явное имя обрезается по краям и проверяется на длину 3–256: вне этого диапазона возникает исключение при запуске, без сокращения явного имени.

Add и Map вызываются один раз, Add предшествует Map. Специальной проверки повторов и конфликтов маршрутов нет: разработчик приложения должен выбрать свободный Path. Если `/health` занят, например, можно задать `options.Path = "/monitoring/health"`; тогда URL проверки заканчивается на `/monitoring/health`.

## Адрес и порт

Если существующий домен уже ведёт в приложение, ожидаемый конечный URL:

```text
https://api.example.com/health
```

В Path указывается только `/health`. Полный URL вводится на стороне UptimeHarbor. **Настройки порта в библиотеке нет.** Порт берётся из существующей конфигурации приложения/прокси и из URL проверки, библиотека не открывает его и не меняет Kestrel.

Для существующего HTTPS server-блока nginx с внешним портом `43871` пример URL:

```text
https://api.example.com:43871/health
```

Ни `43871`, ни внутренний порт приложения не передаются в `AddUptimeHarborHealth`.

## Пример с существующим nginx

Предположим, nginx уже принимает HTTPS на нужном внешнем порту и имеет доступ к приложению по `http://127.0.0.1:18080`. В существующий server-блок можно будет добавить или адаптировать:

```nginx
location = /health {
    proxy_pass http://127.0.0.1:18080/health;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_cache off;
}
```

Это иллюстрация маршрутизации, а не готовый deployment. Внешний порт определяется `listen` уже существующего server-блока. Upstream нужно заменить на фактический адрес приложения; для nginx в другом контейнере localhost обычно указывает на сам nginx. Публикацию контейнерных портов и firewall настраивает владелец приложения, библиотека ими не управляет.

Существующие ограничения nginx должны допускать анонимный GET без login redirect. При унаследованном `auth_basic` может потребоваться `auth_basic off` для этого location. Остальные политики доступа нужно проверить отдельно. Выдача сертификатов не относится к библиотеке.

Если приложение применяет HTTPS redirection за TLS-терминацией nginx, оно должно корректно обрабатывать forwarded headers только от доверенного proxy. Конечный URL мониторинга должен отвечать сразу, без `3xx`. Сохранить действующие границы доверия приложения.

## Ответственность приложения и ограничения

Anonymous metadata endpoint обходит стандартную fallback authorization; это проверено настоящим middleware в памяти, включая авторизованную route group. Собственные middleware, дополнительные финальные conventions, rate limiting, WAF и reverse proxy могут вмешиваться в обработку. Приложение должно пропускать этот маршрут и не менять успешный ответ на страницу входа или HTML.

Ответ использует собственные read-only JSON-настройки библиотеки: ровно `name` и `startedAtUtc`, время с явным +00:00. Изменённые HTTP/MVC JSON-настройки приложения не меняют health; обычный JSON-ответ сохраняет свои naming policy и converter даты. Подробнее — [публичный API](Public%20API.md).

Ответ содержит `Cache-Control: no-store` против стандартного response cache; отдельная endpoint policy отключает стандартный output cache, включая lookup/storage/locking. Проверены оба middleware отдельно и вместе при включённой базовой Cache policy и обычной endpoint convention CacheOutput. CDN/proxy и пользовательские middleware проверяются отдельно; `proxy_cache off` не отменяет все возможные внешние кеши.

Балансировщик может выбирать разные процессы: их время запуска различается. Для мониторинга конкретного экземпляра требуется стабильный URL к нему. Время запуска одного процесса остаётся неизменным между запросами; clock skew проверяющего узла может привести к отклонению времени как будущего.
