# UptimeHarbor.HealthEndpoint

## Назначение и структура

Независимая ASP.NET Core библиотека предоставляет приложению endpoint с JSON-контрактом мониторинга UptimeHarbor.

- `UptimeHarbor.HealthEndpoint/` — проект библиотеки: настройки, снимок процесса и HTTP mapping с изолированным JSON и запретом кеширования. Локальные границы описаны в его `AGENTS.md`.
- `tests/UptimeHarbor.HealthEndpoint.Tests/` — изолированные тесты настроек, lifecycle, middleware и совместимости с исходным checker без запуска хоста; правила находятся в локальном `AGENTS.md`.
- `Documentation/Business logic/` — согласованные требования и границы продукта.
- `Documentation/Technical documentation/` — подтверждённый контракт внешнего потребителя, реализованное устройство библиотеки и ограничения приёмки.
- `Documentation/Plans/` — результаты реализации, зависимости этапов и открытые решения.
- Корневые README, инструкции и `.slnx` — общая навигация; не подключать их повторно через `.csproj`.

## Границы ответственности

- Регистрация зависимостей принадлежит расширению `IServiceCollection`; подключение маршрута — отдельному расширению `IEndpointRouteBuilder` в существующем приложении. Add не подключает маршрут, Map не регистрирует сервисы.
- Библиотека не создаёт listener, не настраивает Kestrel, порты, HTTPS, сертификаты, nginx или firewall. Не использует Docker API/socket, БД или отдельный агент.
- Не создавать зависимости на проекты, DLL или внутреннюю архитектуру UptimeHarbor. Его ограничения MVC, Unit of Work, кластеризации и хранения не являются правилами этой библиотеки.
- Имя и время запуска в ответе относятся к текущему процессу приложения; публичный ответ не содержит секреты, параметры подключений и подробности исключений.
- Библиотека подтверждает только способность приложения отвечать. Проверки готовности БД и других зависимостей не входят в объём.
- Минимальная платформа — .NET 10 / ASP.NET Core 10; .NET 8 и 9 не поддерживать. Совместимость с более новыми версиями подтверждать отдельно.
- Распространять библиотеку DLL-файлом для прямой ссылки из `libs` приложения-потребителя; не использовать NuGet или ProjectReference для её подключения.
- Максимальная длина имени — 256: автоматическое имя обрезается до этого предела, явное после Trim должно иметь длину 3–256 и иначе вызывает ошибку запуска. Дополнительные ограничения на символы не вводить.
- JSON endpoint сериализовать с отдельными настройками, независимыми от настроек приложения. Не обнаруживать конфликты маршрутов и повторные вызовы Add/Map: однократное подключение и свободный Path обеспечивает разработчик приложения.

## Работа с файлами и документацией

- Зависимости и приёмку этапов соблюдать по активному плану. Изолированные тесты не закрывают обязательную внешнюю приёмку; DLL-поставку не начинать до выполнения зависимости этапа 05.
- Исходный `../uptime-harbor/` использовать только для чтения. Не изменять глобальные инструкции, скиллы и память в рамках этого проекта без отдельной просьбы.
- Правки делать точечно через `apply_patch`; сохранять кодировку и окончания строк. Новые документы писать по-русски в UTF-8, имена файлов — по-английски. Проверять отсутствие mojibake, U+FFFD и четырёх вопросительных знаков подряд.
- Каждый новый документ добавлять в тематическое оглавление и соответствующую solution folder `.slnx`. Общая Documentation существует только в корне решения.
- При появлении собственного кода создать содержательные локальные `AGENTS.md` в соответствующих папках. В каталогах только с проектными или документальными файлами пустые инструкции не создавать.
- Изменения ответственности и контрактов отражать в ближайших инструкциях и актуальной технической документации. Завершённые планы сохранять как историю; существующие планы менять только по прямой просьбе изменить именно план.
- Применять `project-planning-docs`, `csharp-project-rules`, `aspnetcore-project-rules` по области работы. Они не расширяют разрешения пользователя.

## Проверка и запуск

Git-команды и проектные скрипты требуют соответствующего явного разрешения. Restore из локального источника, compile-check конкретного проекта и изолированные тесты выполнять в пределах действующего пользовательского исключения для C#/.NET, после статических проверок профильного скилла; повторное разрешение не запрашивать. Не запускать приложение, Docker, сетевые интеграции, pack и публикацию. Не подключаться к БД и не выполнять SQL.

Изолированные тесты используют Microsoft Testing Platform и не запускают хост, listener, внешние процессы или реальные интеграции. Тестовый ProjectReference допустим для разработки; производственное приложение получает DLL из libs. Только тестовый проект компилирует точечные linked sources checker из соседнего репозитория, без его сборки и production-зависимости. Описанные в документах примеры и проверки сами по себе не разрешают запуск. Не объявлять внешнюю HTTP/runtime-приёмку по результатам вызовов middleware в памяти.
